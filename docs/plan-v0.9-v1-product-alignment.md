# ShotgunCV v0.9-v1.0 产品对齐路线

## 目标

接下来几个版本的主目标不是继续证明 pipeline 或 RAG 能跑，而是把 ShotgunCV 从“研发验证型本地工具”推进到“真实用户可连续使用的本地简历工作台”。

核心判断：

- 当前 pipeline、评分门槛、Web 触发、RAG 评测已经具备继续产品化的基础。
- 下一阶段最重要的缺口是用户能否在 Web 中完成真实工作：创建投递、生成可用简历、复核证据、导出结果、回到工作台继续处理。
- RAG、reranker、路由、preservation、性能等指标优化暂缓加强，只保留回归保护和 P0 级阻断修复。

## 产品原则

1. **真实工作台优先**

   Web 首屏应是用户每天打开就能工作的地方，而不是测试页、landing page 或 artifact viewer。页面必须直接回答：现在有哪些投递、哪些需要处理、哪些简历可导出、下一步点哪里。

2. **真实简历输出优先**

   简历生成不能停留在 `summary`、建议、风险提示和改写边界。用户需要可复制、可下载、可投递前复核的完整简历版本。

3. **证据确认优先于继续调指标**

   blocked / needs_review 不应只是结论展示。用户需要补证据、确认硬门槛、标记某条经历可用或不可用，并基于这些确认重新生成。

4. **本地单用户边界不变**

   v1 前不引入多用户、远程队列、自动投递、招聘站账号自动化或 CRM。`run_dir` 继续是业务执行真源，Python pipeline 继续承载核心业务逻辑。

5. **RAG 性能优化冻结到维护模式**

   smart router、reranker、support gate、golden set 继续作为质量门和回归资产存在；除非出现 false positive、no-answer 泄漏、生成引用错误等 P0 问题，不再把 MRR、All Expected、route quota 作为主迭代目标。

## v0.9 真实工作台重构

### 目标

把 Web 首页和核心导航改成真实 operational workbench，而不是展示型首页或测试风格页面。

### 主要方向

- 首页默认展示运行队列、待处理事项、可导出简历、失败运行、需复核门槛和最近完成结果。
- 保留产品说明信息，但降级到次级入口，不占据首屏主位置。
- `/runs`、`/evaluations`、`/resume` 的信息架构统一为“工作队列 + 筛选 + 下一步动作”。
- 所有用户可见文案继续保持中文、业务语言和动作导向，不暴露 `runId`、`jdId`、artifact path 等内部字段，除非位于高级诊断区。
- 空状态必须引导真实下一步：创建投递、补简历文本、检查设置、重新运行，而不是只解释页面用途。

### 验收标准

- 打开首页 5 秒内能判断下一步该处理哪个投递。
- 有 run、有 draft、有 failed、有 needs_review、有 completed report 时，首页都能给出清晰入口。
- 首页不再以产品营销或测试预览作为主体。
- 移动端仍可完成创建草稿、查看失败、进入简历结果和查看报告。

## v0.10 真实简历生成与导出

### 目标

把 `generate` 从“版本摘要和建议”升级为“可使用的简历版本生成”，并在 Web 中提供复核、复制和导出。

### 主要方向

- 新增完整简历版本 artifact，例如 `generate/generated_resumes.json` 或等价结构，包含：
  - 目标岗位或岗位簇。
  - 完整简历正文。
  - 模块化 section：摘要、技能、经历、项目、教育、证书。
  - 每个 section 的来源证据和改写策略。
  - 禁止编造项、待核实补强项、用户确认状态。
- Web `/resume` 从 artifact 编排页升级为简历生成工作台：
  - 按岗位查看完整简历。
  - 对比原始材料、生成版本和风险提示。
  - 一键复制 Markdown。
  - 导出 Markdown。
  - 导出 PDF 或 DOCX 作为 v0.10 后半段目标，优先级低于 Markdown 真实可用。
- 生成规则必须遵守 v0.5.7 的 hard gate 与 fabrication policy：
  - 学历、证书、工作年限、公司、奖项等硬事实缺失时不得补写。
  - 模拟补强必须标记为待核实，不进入真实匹配分。
  - blocked / needs_review JD 默认不生成普通可投递简历。
- 报告页不再是唯一阅读结果，简历工作台成为用户交付物中心。

### 验收标准

- 对通过门槛的 JD，用户可以在 Web 中看到一份完整简历版本，而不是只看到建议。
- 用户可以复制或下载 Markdown 简历。
- 生成简历中每个关键改写都能追溯到候选人证据或明确标记为待核实。
- blocked / needs_review 的 JD 不会产出看起来可直接投递的普通简历。

## v0.11 证据确认与补材料闭环

### 目标

让用户能处理系统不确定性，而不是只被动接受 blocked / needs_review。

### 主要方向

- 在 Web 中为每个门槛项提供用户动作：
  - 确认已有证据。
  - 上传或粘贴补充材料。
  - 标记为不满足。
  - 标记为不重要或不投该岗位。
- 新增用户确认 artifact，例如 `review/user_evidence_overrides.json` 或等价结构；它必须独立于自动抽取结果，避免污染原始 candidate profile。
- pipeline 支持读取用户确认结果重新构建 requirement matrix 和 preflight gates。
- Web 详情页展示“系统判断”和“用户确认”的差异。
- 所有人工覆盖都必须进入报告和导出简历的 provenance，不允许静默覆盖。

### 验收标准

- 用户能把一个 `needs_review` 岗位通过补证据推进到 `pass`，或明确关闭该岗位。
- 用户确认不会修改原始上传文件，也不会让系统把未确认内容当作真实事实。
- 重新运行后，评估页、简历页和报告页都能看到确认来源。

## v0.12 端到端产品 QA 与交付打磨

### 目标

用真实使用路径验证产品，而不是只依赖单元测试和 RAG 指标。

### 主要方向

- 建立 3-5 份真实简历和 20-30 个真实 JD 的本地 QA 套件，覆盖：
  - 文本简历。
  - PDF 简历。
  - 截图 JD。
  - 多 JD 批量投递。
  - blocked / needs_review / pass 混合场景。
- 补齐浏览器级 QA 清单：
  - 首页工作台。
  - 上传草稿。
  - 运行中状态。
  - 失败恢复。
  - 评估复核。
  - 简历生成与导出。
  - 设置页。
- 统一报告与导出体验：
  - 报告用于解释决策。
  - 简历导出用于真实交付。
  - 工作台用于日常处理。
- 设置页必须能清楚诊断本地 Python、OCR、模型 key、模型 endpoint 和导出依赖。

### 验收标准

- 一名非开发用户能从 Web 完成：创建投递 -> 启动评估 -> 处理需复核项 -> 生成简历 -> 导出。
- 真实 QA 套件中不出现明显乱码、内部路径泄漏、英文测试占位文案或无法解释的失败状态。
- 所有失败都有用户可理解的下一步。

## v1.0 发布边界

### v1.0 应包含

- 本地单用户真实工作台。
- 多 JD 输入与批量评估。
- 可解释评分、门槛检查和风险提示。
- 完整简历生成。
- Markdown 导出，PDF/DOCX 至少一种可用导出形式。
- 用户补证据与重新评估闭环。
- 报告、简历、评估结果三类产物角色清晰。
- RAG/review 作为辅助证据层稳定运行，但不是主卖点。

### v1.0 不包含

- 自动投递。
- 招聘网站账号登录或浏览器自动化。
- 多用户协作。
- 远程队列。
- CRM。
- 通用求职问答助手。
- 继续追求 RAG 指标榜单式优化。

## 暂缓项

以下能力进入维护模式，除 P0 问题外暂不作为主线版本目标：

- RAG MRR、Recall、All Expected、All Primary 的继续压榨。
- reranker 模型替换与大规模参数搜索。
- route quota 的持续微调。
- pgvector / PostgreSQL 投影产品化。
- Indeed 或其他招聘站 MCP 导入。
- post-run review 图结构性能优化。
- LangGraph 节点合并、编译缓存等非用户可见性能优化。

暂缓原因：

- 当前 RAG 已经具备可观测、可回归、可解释的基础。
- 继续优化局部指标对最终用户价值的边际收益低于真实简历生成和导出。
- 用户当前最缺的是可用交付物和证据修正路径，不是更高的离线检索分数。

## 推荐实施顺序

1. v0.9：重构首页和核心页面为真实工作台。
2. v0.10：实现完整简历生成 artifact 与 Markdown 导出。
3. v0.11：补齐证据确认和补材料闭环。
4. v0.12：真实端到端 QA 和导出打磨。
5. v1.0：收敛边界、文档、样例和发布检查。

## 成功判断

如果用户完成一次真实投递准备后，能拿到一份可信、可导出、能解释来源和风险的简历版本，并知道下一批岗位该如何处理，那么产品方向正确。

如果系统只是给出更多分数、更长报告、更复杂的 RAG 指标，而用户仍然不能导出可用简历，那么下一阶段方向就是失败的。
